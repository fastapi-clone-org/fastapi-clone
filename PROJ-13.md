# PROJ-13 — Add validation-error response example for constrained query parameters

## Issue type

Story

## Summary

Improve the query parameter validation tutorial by showing the response returned when a string constraint is not satisfied.

## Priority

Medium

## Status

To Do

## Component

Documentation and request validation

## Labels

`documentation`, `query-parameters`, `validation`, `developer-experience`

## Description

The query parameter validation tutorial explains how to configure string constraints, but it does not provide a complete client-facing example of the validation response. Adding a concise error-response example will help API consumers understand the HTTP status, error location, and constraint metadata they should expect when submitted input does not meet the declared requirements.

The change should use an existing constrained query parameter scenario and must remain aligned with the behavior generated by the tutorial application. Focus the work on making the validation contract clear to readers and on preventing the documented behavior from drifting from the example application.

## Acceptance criteria

The tutorial includes a request example that provides a value which violates an existing string query parameter constraint, followed by the corresponding validation-error response. The example clearly communicates that the response has an HTTP 422 status and identifies the invalid input as a query parameter, while presenting the error information in a form consistent with the application’s actual response. The surrounding text explains that validation happens before the path-operation function is executed and does not imply that invalid data is silently accepted or converted.

Focused automated coverage verifies the constrained query parameter’s success path and failure path without changing framework-level validation behavior. The failure assertion checks the response status and the relevant query-parameter error details, and the success assertion confirms that a valid value continues to produce the documented response. The generated API schema remains valid and continues to expose the parameter’s existing validation metadata, and no unrelated tutorials, application behavior, or public API contracts are modified.

## Out of scope

- Introducing new validation constraints or response formats.
- Modifying framework-level error handling.
- Rewriting unrelated documentation sections.

- The acceptance criteria are satisfied.
